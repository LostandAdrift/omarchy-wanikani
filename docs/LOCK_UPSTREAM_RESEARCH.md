# Upstream lock ownership research

Researched **2026-09-05** for the [local incident](LOCK_RELOAD_INCIDENT.md): Omarchy **4.0.2-1**, Quickshell **0.3.1-1**, plugin reload followed by `secure:true`, `sessionLocked:false`, `requested:true`, `pending:true`. Public source and issue reads only; no new host observations, authentication, recovery attempts, postings, or runtime changes.

**The failure has matching upstream reports and proposed fixes. This research did not establish a released fix or a supported, verified recovery procedure for this exact installed state.** Development-branch improvements below are useful leads, not evidence that the installed client has been repaired.

## Confirmed source behavior

- Omarchy's versioned **v4.0.2** `reloadPlugins()` calls `unloadPluginServices()`, which destroys every service without preserving the lock owner. The lock service then declines acquisition when `secure` is true. The restart script refuses while either `secure` or `requested` is true, so its existing recovery branch does not cover the incident's status. These are direct code observations, consistent with the earlier installed-source inspection. [Shell](https://raw.githubusercontent.com/omacom/omarchy/v4.0.2/shell/shell.qml), [lock service](https://raw.githubusercontent.com/omacom/omarchy/v4.0.2/shell/plugins/lock/Service.qml), [restart script](https://raw.githubusercontent.com/omacom/omarchy/v4.0.2/bin/omarchy-restart-shell).
- Quickshell **v0.3.1** distinguishes instance ownership from process-global security. Its reload handoff can retain an old manager when `onReload(oldInstance)` receives the corresponding old object; arbitrary destruction and recreation does not imply that handoff. Its acquisition path proceeds to display surfaces after a failed manager acquisition. These mechanisms support the incident explanation but do not identify the surviving objects on this machine. [WlSessionLock implementation](https://raw.githubusercontent.com/quickshell-mirror/quickshell/v0.3.1/src/wayland/session_lock.cpp), [manager implementation](https://raw.githubusercontent.com/quickshell-mirror/quickshell/v0.3.1/src/wayland/session_lock/session_lock.cpp).
- The v0.3.1 protocol wrapper's destructor destroys an initialized lock without clearing `manager->active`; normal unlock does clear it. That supports the upstream reports' stale-manager explanation; the particular lifetime failure remains an inference for our incident. The official documentation warns that destruction without unlocking can leave a secure but unusable compositor session. [Protocol wrapper](https://raw.githubusercontent.com/quickshell-mirror/quickshell/v0.3.1/src/wayland/session_lock/lock.cpp), [versioned API documentation](https://quickshell.org/docs/v0.3.1/types/Quickshell.Wayland/WlSessionLock/).

## Recovery conclusion and unresolved questions

Issue #6888's author describes a compositor-clear workaround. That is a reporter's emergency action, not an authenticated recovery procedure validated here. PR #7169 explicitly avoids clearing the compositor lock before replacement because doing so drops protection before relocking. No automatic bypass or host action follows from these reports. [Reporter account](https://github.com/omacom/omarchy/issues/6888), [proposal's security rationale](https://github.com/omacom/omarchy/pull/7169).

The remaining questions are which released package contains the complete ownership fix, whether its recovery preserves authentication and compositor protection on this three-monitor setup, and whether an older authentication surface survived the local incident. Public research cannot answer the last question. Continue the project's existing lifecycle deferral while locked, locking, or unknown; that is prevention, not recovery.

Search coverage included the versioned sources, related Omarchy issues/proposals and Quickshell issue links, plus retrieved development sources. Some GitHub history/API fetches were unavailable and web pages can lag current state. No claim of an exhaustive upstream search, definitive root-object diagnosis, or universally safe recovery is made.
